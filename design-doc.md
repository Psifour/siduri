# siduri — password manager over the gilgamesh vault

Siduri stores logins as records in the standard gilgamesh vault. It adds no
cryptography of its own: sealing, per-record AEAD, integrity tags, hardware
binding, and the unlock model are all gilgamesh's (`gilgamesh.kms/v1`).

## Storage

Siduri reads and writes the **same vault file** as the gilgamesh CLI
(`--vault` / `GILGAMESH_VAULT`, default `./gilgamesh.vault`). One identity,
one file, one backup story. Concurrent mutation is already serialized by the
vault's advisory `.vault.lock`; `records_tag` covers siduri's records like any
others (external mutation stays warn-only, per the gilgamesh posture).

### Record schema

- `record_type = "login.v1"` — append-only versioning: schema changes ship as
  `login.v2`, never as silent field changes. (Dotted, not slashed: vault record types cannot contain `/`, which the record AD framing reserves.)
- `record id` = 128-bit random id, hex-encoded — **not** the site name.
  Record ids and types are plaintext in the vault file; a readable list of
  every account you hold is a real leak. All human-readable metadata lives
  inside the ciphertext.
- Payload: JSON.

```json
{
  "name":        "github",
  "urls":        ["https://github.com"],
  "username":    "...",
  "password":    "...",
  "totp_secret": null,
  "notes":       null,
  "tags":        [],
  "created":     "2026-08-31T00:00:00Z",
  "modified":    "2026-08-31T00:00:00Z"
}
```

`name` is unique among `login.v1` records and is the CLI handle. `totp_secret`
is the base32 secret from the provisioning URI; codes are computed (RFC 6238,
SHA-1/30s/6 digits default, overrides stored alongside if ever needed as
`login.v2`).

### Search

Unlock once, decrypt every `login.v1` record, scan in memory. AEAD-opening a
few hundred records costs microseconds; Argon2 dominates unlock regardless.
No plaintext index, no complexity. Decrypted entries live in zeroize-on-drop
buffers for the life of the command.

## Unlock

1. If a gilgamesh agent is running (socket present), use its `vault_*`
   operations — no password prompt, no key material in the siduri process
   beyond the requested plaintext.
2. Otherwise prompt and unlock in-process via the gilgamesh library, exactly
   like the gilgamesh CLI.

## Deliberate non-feature: derived per-site passwords

No `app/login/<site>` deterministic passwords. Rotation after a site breach
would need a counter scheme fighting the append-only label rule, and sites
impose incompatible composition rules. Passwords are random, generated by
`gen`, and stored. Derivation is for keys; the vault is for passwords.

## CLI

```
siduri add <entry>            prompt for url/username; password prompted or --gen
siduri show <entry>           metadata; password only with --reveal or to a pipe
siduri edit <entry>
siduri rm <entry>
siduri ls
siduri search <query>         name, urls, username, tags
siduri clip <entry>           clipboard, cleared after 30s (best effort)
siduri totp <entry>
siduri gen [--words N | --length N --charset ...]
```

Secrets never on argv (same hidden-flag + warning posture as gilgamesh; env
vars for scripting).

## Browser extension (phase 2)

```
extension (MV3)  ⇄  native messaging host (small Rust bin, JSON over stdio)  ⇄  gilgamesh agent socket
```

- The native-messaging manifest pins the extension id; the browser can only
  reach the host binary, the host only the agent.
- Requires the agent: the extension never sees the vault password.
- Matching: registrable domain (eTLD+1) + scheme, `https` only; exact-origin
  entries preferred over domain matches.
- Fill only on an explicit user gesture (popup/toolbar click). Never on page
  load, never into cross-origin subframes. These three rules are the point:
  origin-bound fill is phishing protection a clipboard can't give.
- Nothing in `chrome.storage`, no sync; credentials exist only transiently in
  the popup.
- Chrome and Firefox share the codebase; only the host-manifest format
  differs.

## Threat notes

- The vault file remains ciphertext-or-public; siduri adds only the
  plaintext-id consideration handled above.
- Clipboard is a shared channel: `clip` warns once about clipboard-history
  managers; timed clear is best effort.
- TOTP secrets in the same vault as passwords means the vault is a single
  factor bundle; that is accepted (the alternative — a second identity — is
  not worth the ceremony for this threat model). Users who want the second
  factor elsewhere simply don't store `totp_secret`.

## Status

Implemented: all CLI commands, agent-first backend with in-process fallback,
TOTP (RFC 6238/4226 vectors tested), generator, clipboard with timed
compare-before-clear. Phase 2 (browser extension) not started.
